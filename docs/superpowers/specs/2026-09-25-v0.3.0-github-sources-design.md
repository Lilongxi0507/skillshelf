## 1. 目标与明确结论

### 1.1 用户要的结果

SkillShelf 成为一个独立的、本机共享的完整技能管理器：用户在 CLI 中选择技能，系统从审核过的 GitHub 固定提交取得完整内容，保存在持久本地库，接入多个 Agent；后续可以预览更新、固定版本、回滚、冻结项目和离线迁移。

用户不应为每个技能维护一个 npm 包，也不应手工寻找、复制上游文件。

### 1.2 推荐方案

1. 新目录中的 **83 项技能、8 个逻辑技能包全部使用 GitHub 固定 commit 获取**。
2. 新版 npm 发布常规只涉及两个身份：`@llx17669475/skillshelf`（CLI）和 `@llx17669475/skillshelf-catalog`（元数据目录）。
3. 8 个逻辑包仍保留，它们不是 8 个必须发布的 npm 包；整包安装/更新/回滚，成员按需启用和读取。
4. 保留旧 npm 获取路径，用于已发布版本、旧安装历史、旧锁和离线恢复。**新目录默认 GitHub，不等于删除 npm 兼容代码。**
5. 上游更新不自动落到用户电脑。默认走“发现变化 → 审核 → 发布目录 → 用户确认更新”。
6. CLI、目录、每个逻辑包的版本独立，不再因一个技能更新而重发所有包和 CLI。
7. v0.3.0 上线包括真实公共安装和验证，不以“本地 build 成功”代替上线。

### 1.3 为什么选这个方案

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 继续给所有技能发 npm 数据包 | 现有代码变化小 | 重复分发、多包发布耦合、新身份受限 | 仅保留旧版兼容 |
| 每次安装直接追踪 GitHub main/tag | 更新快、看似简单 | 文件会漂移，审核、锁定、复现和回滚不可控 | 不采用 |
| 审核目录 + GitHub 固定 commit | 减少发布负担，来源清楚，保持可复现 | 需要来源校验、映射、缓存和迁移实现 | **采用** |

### 1.4 两点事实修正

- 现有 GitNexus 包不是整个 GitNexus 软件，仅包含选定的 13 项技能；CLI/MCP 运行时一直是独立依赖。
- 两个第一方工具的适配快照已经在独立 SkillShelf 源码树的 `skills/` 下；它们不是必须另外建新仓库。新设计要把下载定位改为这个独立仓库的公开固定提交，不能使用旧 `clients/skills/...` 的面板来源路径作为下载地址。

## 2. 版本与术语：以后到底更新什么

| 名称 | 意义 | 示例/规则 |
|---|---|---|
| CLI 版本 | 管理器本身的程序版本 | `0.3.0`；程序行为变化才需要升级 |
| 目录版本 | 一次审核后的推荐集合 | 首次 `0.3.0`；之后可单独发布 `0.3.1`，CLI 仍为 `0.3.0` |
| 逻辑技能包 | 同步安装和版本切换的一组完整成员 | taste、superpowers、gitnexus 等 8 包 |
| 包修订号（packRevision） | SkillShelf 审核发布的包内容修订 | 正整数 `1`、`2`…，按包独立增长，展示为 `r1`、`r2` |
| 上游版本标签 | 上游维护者的版本说明 | 可显示，但不作为最终获取身份；标签可被移动 |
| 固定提交（commit） | 下载所依据的确切 GitHub 提交 | 完整 40 位 SHA；不把 branch/tag 写入安装锁作为身份 |
| 获取描述（acquisition） | 从哪里、如何取得所需字节 | 来源类型、仓库、commit、路径映射、许可补充来源 |
| 来源归属（provenance） | 谁编写、从哪里改造、适用许可 | 与获取地址分开；第一方改造保留原始归属 |
| 内容摘要（contentDigest） | 规范化完整清单和内容的校验身份 | 定义需版本化，不与压缩包字节混为一谈 |
| 发布身份（releaseId） | 区分同名、不同来源和不同修订的安装记录 | 完整摘要绑定获取描述、清单和安全相关元数据 |

规则：

- GitHub commit 不参与 SemVer 大小比较；由目录明确推荐哪个包修订。
- 目录只改中文介绍、分类、搜索标签时，不触发已安装技能内容更新。
- 选中文件、成员布局、许可、运行入口、依赖要求或获取来源变化时，需要新的包修订和差异审查。
- 同一个包修订一旦发布不得指向不同内容；发现同修订不同摘要必须拒绝。
- 不把旧 `0.2.1` npm 版本偷偷改写为 GitHub `r1`；迁移产生新发布身份，旧身份保留。
- 精确身份的内部校验使用完整摘要，不靠显示用短 commit 或短摘要判等。

## 3. 技能更新后，你该怎么办

### 3.1 普通使用者：检查、预览、确认三步

以下为 v0.3.0 目标用法；沿用的命令会扩展 GitHub 来源支持，新增命令已标注。

```bash
# 1. 看是否有审核通过的新修订：只读，不下载技能、不写本机目录
skillshelf check

# 2. 看具体变化：文件、成员、来源、依赖、许可、运行入口
skillshelf update taste --dry-run

# 3. 确认更新；只处理所选包，不更新 CLI
skillshelf update taste --yes

# 如要更新全部已装且未固定的包
skillshelf update --dry-run
skillshelf update --yes
```

v0.3.0 的预览应显示：

- 当前 `r1 / commit A` → 推荐 `r2 / commit B`；
- 新增、删除、改变了哪些成员和文件；
- 是否变更许可证、运行入口、依赖、网络需求；
- 哪些 Agent 受影响、哪些项目保持冻结、哪些包因 pin 跳过；
- 是否已有缓存、预估网络体积是否未知；不能把选中文件体积冒充下载体积；
- 当前副本是否被改动、是否存在路径冲突；
- 确认后将使用的确切目录和包修订。

`--dry-run` 不改变技能、Agent 目录、状态、项目锁或持久缓存。GitHub 文件清单随目录元数据提供，因此预览不必为了计算差异提前把技能装入 store。

交互式预览与执行必须绑定同一份目录/状态指纹；期间如果目录、锁或本机状态变化，则拒绝应用旧计划，重新预览。自动化脚本分开执行 `--dry-run` 和 `--yes` 是两次独立请求；若要求跨请求完全一致，可使用已有全局 `--catalog` 指定同一个经过审核的本地目录快照，执行报告始终返回实际采用的精确身份。

### 3.2 不想更新：固定当前版本

```bash
skillshelf pin taste --yes
skillshelf check
skillshelf update --yes
```

`check` 仍可提示更新，但 `update` 必须跳过固定包，不能以“安全更新”或“来源迁移”为由自动解除 pin。

需要升级时：

```bash
skillshelf unpin taste --yes
skillshelf update taste --dry-run
skillshelf update taste --yes
```

### 3.3 更新后不好用：回滚并固定

```bash
skillshelf history taste                         # 新增：列本地已保留历史
skillshelf rollback taste --dry-run
skillshelf rollback taste --yes
skillshelf pin taste --yes
```

- 默认回到上一个已保存且校验通过的发布身份，不联网。
- 新增 `rollback --revision <releaseId>` 精确选择 GitHub/legacy 历史；旧 `--version` 继续用于旧 npm/本地 SemVer，歧义时拒绝并列候选。
- 回滚保持已有 pin 状态，不自动加 pin；因此示例显式执行 pin，防止下一次更新又升回去。
- 若历史对象被损坏或在外部被删，明确报告；不能声称任何情况下都能离线回滚。

### 3.4 项目要求长期稳定

```bash
skillshelf install superpowers --project "<项目绝对路径>" --agent codex --yes
skillshelf sync --frozen --project "<项目绝对路径>" --yes
```

- `skillshelf.json` 表达选择意图，`skillshelf-lock.json` 记录精确修订、commit、映射和清单身份。
- 全局更新不改变项目锁。
- 更新项目必须显式指定项目，先预览后更新其声明和锁。
- `sync --frozen` 只恢复锁定版本，不升级、不重写锁、不追随当前目录推荐。
- 团队成员可提交锁文件复现；锁中不得包含 Key 或用户电脑绝对路径。

### 3.5 上游已经更新，但 SkillShelf 还没推荐

这是两种不同状态，界面必须区分：

1. **上游存在候选变化，但尚未审核**；
2. **SkillShelf 已审核，可以升级到某个包修订**。

普通 `check/update` 只处理第 2 种，不把上游最新 commit 自动当作安全版本。

维护者可执行新增命令：

```bash
skillshelf sources check                         # 新增：检查上游候选，默认不写文件
```

该命令不安装候选、不更新 pin、不调用技能代码。其联网结果标记检查时间、上游候选 SHA、GitHub 配额/可用性；`--offline` 下只报告未检查/已有信息，绝不声称最新。

急需尚未审核版本的高级用户，可先单独审查上游并通过现有本地 author/import 流程隔离试用。v0.3.0 不提供绕过审核的 `update --latest-main`，也不授予这种本地内容第一方执行资格。

### 3.6 自己修改过技能

受管 store 不是编辑区：

```bash
skillshelf fork taste --output "<新的可编辑目录>" --yes
```

- fork 后作为本地内容管理，不随公共目录更新。
- 已改动的 Agent copy 或被改向的 link 必须保留并报告冲突，不覆盖。
- v0.3.0 不自动三方合并技能；显示来源和差异后由用户决定。

### 3.7 更新的是 CLI，还是技能？

```bash
skillshelf self-update --check
npm install -g @llx17669475/skillshelf@0.3.0
```

CLI 由 npm 升级；技能由 `skillshelf update` 更新；`catalog refresh` 只换目录元数据。三者不得互相隐式升级。后续目录版本可以比 CLI 版本高，只要 `minCliVersion` 和 schema 能力兼容。

## 4. 维护者如何发布技能更新

### 4.1 审核流程

```text
上游 release/tag/branch 有变化
  → 解析候选为完整 commit SHA
  → 只读下载并比较选中范围
  → 审查文件、脚本、依赖、跨成员引用、LICENSE/NOTICE
  → 重建路径映射和完整清单
  → 内容变化的包增加 packRevision
  → 自动测试 + 人工审核
  → 发布新的 catalog 版本
  → 用户 check 看见更新，确认后安装
```

仅内容变化时，通常只发布一个 catalog npm 新版本，不重发 CLI，也不发布技能 npm 数据包。

### 4.2 自动化范围

- 提供维护脚本：检查上游、生成候选差异、验证来源、生成目录和更新说明。
- 仓库 CI 可定时做只读上游检查并保存结果；联网失败标为失败/未知，不能吞掉后给绿灯。
- 普通 PR/定时任务不持有发布权限，不自动合并、不自动发布。
- 正式发布保持审核后的手动 GitHub Actions/OIDC 触发。
- v0.3.0 不做自动审查通过，也不宣称能自动发现所有恶意技能代码。

### 4.3 特殊变化

| 变化 | 默认行为 |
|---|---|
| 同仓库其他代码变化，选定技能没变 | 不因为 branch 变化给用户制造升级；保留原固定 commit 即可 |
| 技能新增成员 | 作为新修订审查；保留已有目标的启用状态，新成员默认不自动进入旧目标 |
| 删除/重命名已启用成员 | 阻止无提示更新；展示影响，确认迁移或先停用 |
| 仓库转移/改名/路径变化 | 视为来源变更，经新目录审核；不自动跟任意 redirect |
| 根 LICENSE/NOTICE 改变 | 重新审查并在更新预览中突出显示 |
| GitHub tag 被移动 | 已装版本/锁不动；候选检查只提示变化 |
| 上游历史/仓库不可访问 | 不换源、不升级；已缓存可用，未缓存明确失败 |
| 紧急撤回推荐修订 | 目录可标记 withdrawn，提示已有用户并阻止新常规安装；不自动删除本机内容或悄悄改锁 |

## 5. v0.3.0 完整功能清单与边界

“完整”指本表中的必做范围全部验收，不代表把所有未来功能纳入同一版本。

| 功能区 | v0.3.0 必须交付 | 范围/限制 |

| 项目复现 | 项目声明/锁、frozen sync、全局/项目隔离 | 不静默重写旧锁 |

| Agent 接入 | detect/list/add/remove、connect/enroll、inventory/verify、待重载状态 | 自动目录检查与原生 Agent 正文读取证据分开 |
| 去重/恢复 | 仅完整树相同才可去重，先备份，支持 restore | 不接管未知文件/异内容同名技能 |
| 本地创作 | author create/validate/publish/remove、本地导入、fork | author publish 只入本机库，不上传 GitHub/npm |
| 任务组合 | profiles save/list/apply/remove，明确成员选择、冲突预检 | 是选择模板，不是版本锁；版本复现用项目锁 |
| MCP 定义管理 | stdio/HTTP 定义、启停、env 引用、诊断、配置预览 | 不冒称已完成所有原生配置写入或常驻共享进程 |
| SkillShelf 只读 MCP | 新增 `mcp serve`，接通现有 search/info/read/doctor 只读发现实现 | 不增加经 MCP 远程安装/执行权限；用真实双会话测试 |
| 第一方工具 | 搜索、图片/视频工具继续可用，新增 GitHub 来源执行证据验证 | 仅审核的两个工具；不自动安装 Python/依赖 |
| Provider 管理 | 本地配置、env Key 引用、去敏、私有权限、显式 run | 不自动发计费探测，不重试结果未知请求 |
| 离线能力 | 本地 search/read/status/verify、已有内容离线安装/恢复、完整 bundle | 首次 npm 安装和未缓存 GitHub 内容仍需网络 |
| 维护与恢复 | doctor、verify、repair、gc、home 迁移、uninstall | 保留用户改动、历史、项目引用和备份 |
| 上游维护 | sources check、目录候选生成与差异审核、catalog-only 发布流程 | 普通用户不直接跟 main 自动更新 |
| 交付与发布 | Linux/macOS/Windows CI，真实 public smoke，npm 双包发布与回读 | 未测试平台/Agent/付费服务必须明确标注 |

### 5.2 原有功能必须修正的表述和行为

- 当前 MCP diagnose 返回 `protocolProbe: not-run`，preview 不修改原生 Agent 配置。v0.3.0 保留诚实状态；普通 doctor/diagnose 不暗中启动程序或访问外部服务。
- 当前 profiles 中保存的 MCP 字段没有实际应用逻辑。v0.3.0 不静默承诺支持：对非空而不支持的 MCP 组合明确提示/拒绝，并保留原配置；技能组合要补前置冲突检查和清晰失败/恢复报告。
- Agent verify 的目录读取不等于原生客户端加载；必须展示两种证据，原生未测时标记未验证。
- core 模块的只读/计划/应用 interface 必须与 CLI 行为一致，保留一次性计划及状态指纹校验；不是另建一套状态。

总计 83 成员、8 逻辑包、7 个主来源仓库。许可补充可能也来自 SkillShelf 固定提交，必须在获取描述中显式记录。

### 6.1 不能只把 source.path 直接下载

现有快照包含以下处理，迁移必须重现：

- Taste、UIUX 等将上游根 LICENSE 复制到成员目录；
- GitNexus 保留非商业许可和要求的版权 Notice；
- Archify 有补充的 THIRD_PARTY_NOTICES，品牌素材并非统一 MIT；
- 本地快照目录名、成员 ID 和上游目录名可能不同；
- 第一方两个工具是独立适配后的内容，而不是直接下载原面板目录。

因此新来源需要显式“路径映射 + 附加文件来源”，而不是单一 `path` 字段。

第一版仅支持：复制一个完整选定目录、复制声明的许可/Notice 文件到固定目标路径、保持清单规定的执行位；**不支持任意 patch 脚本、postinstall、执行模板代码**。补充文件也必须来自已固定的 GitHub 提交或明确的、确定性的元数据生成规则，并纳入清单校验。

### 6.2 GitHub 直取不等于只下载子目录

codeload archive 通常是某个提交的仓库归档，网络下载可能覆盖整个仓库，之后才筛选需要的目录。

v0.3.0 默认方案：按 `repo + commit` 流式下载/扫描一次，在本地只保留需要的完整树。同提交共用缓存/下载任务，不为每个成员重复下载。

必须先测量各固定仓库归档的实际体积。若个别仓库超过经过审查的资源预算，该来源不能以“83 项全支持”带病上线；必须在来源验证阶段单独选择并审核精确文件/树获取方案，重新测试后才纳入。不得临时无限放大限制、偷偷添加第三方镜像或谎称已按目录节省网络流量。

## 7. 来源与安全模型

### 7.1 统一获取 Module

在现有获取入口建立一个小 Interface，内部使用三个实际需要的 Adapter：

- GitHub 固定提交 Adapter：新目录默认；
- legacy npm Adapter：旧版本和旧锁；
- 显式本地 fixture Adapter：隔离开发测试，不流入公共目录。

Interface 的职责是：接收已验证的发布描述，返回完整验证过的内容对象及获取收据。下载、限制、路径映射、许可补充、去重缓存、临时文件和错误分类留在 Implementation 内；调用方不应自己猜来源或散落下载逻辑。

manager/CLI/project/bundle 继续通过同一 Seam 取得内容，并交给现有事务与投影逻辑。

### 7.2 目录与清单

新目录 schema 明确包含：

- 来源类型和固定仓库/commit；
- 一个或多个审核过的路径映射；
- 包/成员稳定 ID、包修订、成员布局；
- 全部所选文件的路径、SHA-256、长度、执行位；
- 来源描述摘要、内容摘要、运行需求、许可和审核说明；
- CLI/schema 兼容要求。

完整清单是元数据，不包含技能正文、脚本内容或 Key。可以随目录包采用按包 manifest JSON 存储；目录包 allowlist、体积限制和 bootstrap 加载要同步扩展。v0.3.0 的目录/manifest 元数据总量预算为 4 MiB，CI 测量超限必须停止并审查结构，不能无界加载。

### 7.3 GitHub 压缩包不是最终内容身份

GitHub 相同 commit 的 gzip/tar 表示可能变化。因此：

- 核心信任来自受审目录中固定的来源描述与完整文件清单，不靠“仓库名字看起来官方”；
- 接收时验证所有选中文件及其数量、路径、大小、SHA-256 和执行位，拒绝缺失或多余内容；
- 传输层 SHA-512 可保存为本次下载收据，用来校验本地缓存；它不能取代文件清单，也不能因重新压缩变化就更新已审内容身份；
- 新 GitHub 发布身份不依赖 gzip header/mtime；legacy npm 仍严格校验原始 tarball SRI；
- 通过校验的目标树可写入确定性本地快照，方便离线恢复；这不是新的公共 npm 技能包。

### 7.4 网络与归档门禁

- 运行时仅使用程序构造的 HTTPS `codeload.github.com` 固定仓库/commit URL；不接受任意下载 URL，不向下载请求附加发布凭据。
- branch/tag 仅可用于维护者“发现候选”，解析成完整 SHA 后才能进入发布目录。
- 仓库转移、404、403、429、TLS/超时独立报错；不自动换仓库/镜像；尊重 Retry-After，无紧密重试。
- 不要求用户安装 Git；不 clone 仓库、不执行 Git hooks，不递归取 submodule。
- 流式限制：初始候选预算为仓库压缩 128 MiB、流式展开 512 MiB、100,000 entries、总请求 180 秒、空闲 30 秒；仅选中的单文件/整包继续使用现有 16 MiB/64 MiB/2,000 文件预算。预算需用真实来源数据和低内存测试验证后冻结，不把整个 repo 展开放入内存。
- 所选树内禁止 symlink/hardlink/device/FIFO/路径穿越/大小写和 Unicode 别名/特殊 Windows 路径；任何祖先 link 也不能被跟随。
- 未选中范围里的 symlink 不解析、不写盘、不跟随；保留全归档的解码/体积/路径安全检查。不能因为 UIUX 仓库的未选 gallery 链接就误判所选技能损坏。
- 选中内容涉及 LFS pointer、submodule 或缺失资源时，明确不支持并阻止入库；不把 pointer 当成完整资源。
- 下载中断只留下私有 staging；校验通过后才能提交 store、state 和 Agent 入口。

### 7.5 第一方 run 权限

`origin: github` 本身不产生执行资格。第一方工具必须同时满足：

1. 身份为两个明确允许的第一方工具之一；
2. 获取仓库是审核过的独立 SkillShelf 仓库；
3. commit、路径、清单、入口与当前可信目录或已登记的可信安装证据完全一致；
4. 执行前复核实际树和私有配置；
5. 没有通过 fork、bundle 自报字段或修改锁绕过审核。

导入 bundle 的自述来源、commit、hash 不是作者认证。只有与本机已有可信目录/安装记录精确匹配时才保留第一方执行资格；其他导入可以作为本地内容读用，但不能自动获得 `run` 权限。离线恢复到全新机器且无法建立信任时，必须明确提示“内容已恢复，第一方执行待重新授信”，不能伪装完全授权。

## 8. 缓存、离线、共享和恢复

- 成功安装后日常读取不依赖 npm/npx 缓存，也不需要 GitHub 在线。
- 同一 repo+commit 在同一获取任务中去重，同一内容对象供多个 Agent 使用。
- 全仓归档作为可回收的获取缓存；已选择的完整快照、manifest、receipt 和历史按引用保留。
- gc 不能删除当前选择、项目锁引用、回滚历史、待恢复事务所需内容；先预览后清理。
- `export --bundle` 携带选中的已验证内容、清单和恢复所需收据；不把整个 GitHub 仓库、Node、CLI、Provider Key、生成物、其他机器 Agent 绝对路径打进去。
- bundle 导入校验全树，不自动接入 Agent、不自动执行技能。
- `sync --frozen --offline` 在已有对象或可信 bundle 恢复后可用；缺对象时报明确错误，不访问网络。
- 多目录切换仍是写前日志+补偿恢复，不承诺跨盘原子性；跨平台文件占用失败要保留现场并提供 repair 路径。

## 9. 旧版本迁移与回退

### 9.1 三类旧数据都要覆盖

1. 正在使用的公开 `0.1.0-preview.2` schema1 单技能安装；
2. 本地/部分公开的 `0.2.x` schema2 整包、pin、history、project lock；
3. 旧占位 namespace、panel 导入、本地 draft/fork 等非官方 npm 来源。

第 3 类不得靠改名字变成官方 GitHub 可信内容，仍走显式本地导入或新 home 策略。

### 9.2 schema 策略

- 引入新 catalog/state/project-lock 表达 GitHub 发布身份；旧 schema1/2 保持专门读路径，不通过放宽字段任意接受混合数据。
- `list/status/check` 读取旧 home 不触发自动迁移。
- 首次需要新格式的写操作先生成迁移预览、旧账本备份和恢复说明，确认后在事务内更新。
- 新 `migrate sources` 提供全局或指定项目的 npm → GitHub 预览/执行；处理旧单技能 → 整包转换时，列出新增成员但保留原目标的启用选择，不自动暴露整包新成员。
- pin、禁用目标、项目冻结必须保留；固定旧版本默认不迁移来源，先告知用户显式 unpin。
- 来源改变但文件相同，仍保留不同发布身份；有证据可复用同一个内容对象，但不得覆盖旧 origin/receipt。
- 已有 legacy lock 的 `sync --frozen` 继续按原 npm 版本恢复，不因为新目录换 GitHub 就改写或下载新 commit。

### 9.3 降级与回退

迁移后的 home 不保证能被旧 CLI 写入。升级前导出 bundle，保留旧账本/声明/锁备份；降级必须停用新投影并在独立恢复目录操作，不能直接让旧 CLI 覆盖新 schema。

v0.3.0 需要提供一次实测迁移→回滚恢复演练记录，而不仅是“理论兼容”。

## 10. 0.3.0 发布与后续目录独立发版

### 10.1 首次来源快照不能自引用当前提交

第一方技能与补充许可文件需要一个已经公开存在的固定 commit。若 catalog 填自己的最终 commit，会出现内容改变导致 commit 变化的循环。

采用两步：

1. 来源提交 S：固定第一方完整内容、许可和需要的补充文件，提交并公开核验；
2. 发布提交 R：目录引用 S，并固定所有第三方提交；构建 0.3.0 CLI/catalog。

S 可以是一个已存在、内容核验匹配的公开提交；不为了“新版本”机械生成无意义提交。第三方源文件不再为了每次 catalog 更新重复上传到 npm，是否清理仓库中的旧第三方快照另行审查，不作为本次强制删除项。

### 10.2 首发步骤

1. 完成设计/实施计划、开发、代码复核、来源和许可证审核；
2. 从公开固定提交重新取得 83 项内容，与预期清单核验；
3. 冻结来源快照 S 和目录；
4. 生成真实 catalog/CLI tarball，检查无技能正文、凭据、临时目录和内部维护材料；
5. 原生 Linux/macOS/Windows × Node 22/24 使用同一候选验证；
6. 手动 OIDC 工作流先发布 catalog，再发布 CLI，版本精确为 0.3.0；
7. registry 回读 exact version、latest、下载的 SHA-512、provenance；
8. public smoke 使用 `@0.3.0`，不只用 `@latest`；
9. 验证全 8 逻辑包、83 成员真实从 GitHub 固定提交安装，共享、更新/回滚、锁与离线恢复；
10. 在服务器独立安装前缀安装精确公共版本，先备份/预览再迁移已有共享库；不把开发 dist 当上线版本；
11. 同步 README、安装指南、验证矩阵和发行说明，保留可回退记录。

若 catalog 发出但 CLI 失败，记录“部分发布”并停止，不谎称完成；不覆盖同版本不可变 artifact。旧 CLI 面对新 schema/minCliVersion 应明确提示升级且保留原缓存，不能损坏本地数据。

### 10.3 后续技能更新发版

catalog-only 工作流独立指定目录版本和兼容 CLI 范围，审核未变化技能不重新分发。打包校验、测试、发布计划不再要求所有包版本等于 CLI 版本。

现有已发布 0.2.1 的 7 个技能包保留，不删除、不重打；停止创建被限流的 GitNexus npm 身份。0.2.1 的部分发布状态留作历史事实，不拿 v0.3.0 覆盖它。

## 12. 必须覆盖的测试矩阵

### 12.1 来源和完整性

- 固定 commit 正常获取；branch/tag/短SHA/任意URL拒绝。
- 同 commit 的归档压缩表示变化但选中内容相同可验证；任一文件字节变化拒绝。
- 缺失/多余文件、大小写冲突、Unicode别名、重复tar entry、路径穿越、链接、硬链接、设备、压缩炸弹与超时。
- 未选中链接不跟随也不错误提取；LICENSE复制、NOTICE补充、Archify第三方许可、跨成员引用完整。
- 404/403/429、断网、错误重定向、LFS/submodule，来源异常不改变现有状态。
- 缓存命中、并发同commit获取、同内容不同来源身份、损坏缓存的明确诊断。

### 12.2 生命周期和兼容

- 8包83成员首次安装/再次安装；多个Agent共享，不重复按成员下载。
- check零写入、目录refresh不换技能、update dry-run无持久写入、执行前指纹重检。
- catalog-only升级、只更新一个包、展示性metadata改变不制造全部技能升级。
- pin/unpin、禁用目标、新成员不自动启用、删除已用成员的确认、用户改动保护。
- rollback/history、精确revision、旧npm SemVer历史、source迁移撤回。
- schema1/2旧state与锁；全局升级不动项目；frozen不改锁；项目在无当前catalog时依锁恢复。
- 事务各阶段强杀、锁竞争、Windows文件占用、journal恢复。

### 12.3 离线与执行

- 已缓存GitHub/npm对象离线安装；bundle导入全新home；未知信任仅恢复为本地内容。
- provider Key/绝对路径/输出不进入bundle或公共包。
- GitHub同名/改造fork/自报trusted的bundle不能获取第一方run权限。
- 两个第一方工具Python最低版本、帮助和mock协议回归；付费请求另行授权后验证，不作为偷偷调用的CI测试。
- 只读MCP真实双会话初始化、tools/list、读取指定正文；不允许写入/执行工具。

### 12.4 平台与产物

- Linux/macOS/Windows × Node 22/24；补最低 Node 22.20.0 和 Python 3.10 验证。
- POSIX PTY 40/80/120列、取消、中文、NO_COLOR；Windows原生命令/ACL/路径/占用。
- 新增完整回归入口，缺开发目录/CLI tarball/临时测试目录时失败，不能以大量skip假绿。
- 每个新版schema、迁移和来源安全拒绝分支有回归用例；发布任务仅允许事先列明的平台条件skip。
- 同一来源清单和候选包在多平台核验；公共smoke逐包而非只测taste。
- fresh public CLI安装、目录下载、真实GitHub安装、verify、pin/rollback、project sync、bundle。

## 13. “完整 v0.3.0 上线”的定义

只有同时满足下列条件，才能对用户说已经完整上线：

1. 83成员/8逻辑包都可按审定GitHub固定来源获取，并保留完整内容和许可。
2. 新获取、更新、pin/rollback、项目锁、离线bundle、legacy npm兼容通过测试。
3. 第一方工具权限不因来源转换被扩大；任何未验证/付费场景没有被冒称通过。
4. CLI/TUI/JSON和文档与真实行为一致；新增命令全部可执行。
5. 三平台CI使用候选实际通过，没有未解释的失败和被隐藏的核心skip。
6. catalog与CLI两个精确0.3.0公共包可下载，SHA-512与冻结计划匹配，latest指向正确，发布证据可追溯。
7. public smoke与全包真实获取验证通过；服务器运行的是精确公共版而不是开发dist。

## 14. 本版不包含

- 私有GitHub仓库登录与Token管理、任意URL/任意镜像安装；
- 不审核就跟随main自动升级、自动合并上游代码；
- 自动安装GitNexus/Archify/Agent/Python/Node等外部运行时；
- 自动执行第三方技能、创建hooks、授予项目信任；
- 技能本地改动自动三方合并；
- 云同步、账户系统、团队服务端、商业技能市场；
- 全能MCP运行时代理/进程复用服务、对所有Agent的原生配置自动写入；
- 新Web/桌面GUI；
- 把原生平台/Agent不可用、付费provider未测说成已完成。

这些范围不是偷偷删功能，而是把现有“预览/未接通/未验证”与本次新增GitHub分发能力明确分开，避免一版承诺无限扩张。

## 15. 审阅与执行门槛

本计划的推荐默认决策如下：

1. **审核后更新**，不是实时跟随上游main。
2. **全部83项迁移**，两个第一方工具使用已公开的独立SkillShelf快照，不取面板源码或私有数据。
3. **npm只发布CLI/catalog**，旧npm技能包保留兼容，不删除已发布版本。

5. **v0.3.0结束必须包含上线验证**；付费请求和未能访问的真实客户端不冒充已验收。

用户确认本书面设计后，下一份逐文件实施计划会给出具体测试、改动模块、迁移顺序和发布命令；确认实施计划/执行方式后进入开发，不再停留在口头规划。默认建议在当前会话使用隔离工作树、按阶段实现并做独立复核。
